Typography & Hierarchy

Font: Inter, closely matching Calibri/Helvetica Neue in the existing deck. Pillar names (GOVERN / AUTOMATE / SCALE) are the primary H1 of each column — 800 weight, uppercase, navy. This deliberately inverts the old design where the stat number was the H1. Value proposition leads; evidence badge follows.

Evidence badges: The numbers (6, 14, ∞) live inside lozenge badges at secondary hierarchy, alongside the pillar name. In PowerPoint: a rounded rectangle shape (navy outline, card-fill), small text label. "∞" uses outlined text (navy stroke, transparent fill) to signal limitlessness vs the hard counts 6 and 14.

Circle icons: White vector icons on navy circles — same grammar as CVS timeline slides. Icons are 46% of circle diameter. No connector line between circles: the three pillars are parallel propositions, not a sequential flow.

Layout & Flow Visual

Slide structure (top to bottom): header → transformation flow → three support pillars → footer. The flow is the hero — it tells the product story in one glance before the audience reads a word.

Transformation flow (three nodes + two arrows): "Before" node (Legacy ACE, warm grey tint, amber left border) → "AI-Powered" arrow → factory node (navy fill, white text, shadow — visually dominant) → "Production-Ready" arrow → "After" node (Spring Boot, green tint, green left border). The factory node takes 1.3× the width of the flanking nodes to signal it is the subject. The flanking nodes' colour warmth (legacy=amber, modern=green) creates a problem→solution gradient without labels.

Three pillars: GOVERN / AUTOMATE / SCALE — each with navy top border, icon circle, evidence badge, body text, and callout. These are support detail, not the story. They answer "how does the factory work?" after the flow answers "what does it do?"

Footer (single ruled row): tagline left, CVS logo centre, copyright right. Clean, consistent with existing deck convention.

GOVERN (left pillar) — 25 sec
Point to the Govern pillar. "Every approval in this system is cryptographically locked to the exact artefact the approver reviewed. If that document changes after sign-off — even by a single character — the approval is automatically invalidated. There are no stale approvals. Six mandatory human checkpoints gate every migration. Every agent action, every decision, every approval is recorded in a tamper-proof, hash-chained audit ledger. AI accelerates. Humans decide. Always. No AI output governs a production decision without a named human gate."

AUTOMATE (centre pillar) — 25 sec
Point to the Automate pillar. "Fourteen specialised AI agents drive the full migration pipeline — from the moment we discover an ACE service to the moment a Spring Boot microservice is production-ready. Each agent operates within a declared, audited authority boundary it cannot exceed. Agent contracts are hashed at startup — any unauthorised modification fails initialisation. Before any generated code advances, we run live differential testing: the original ACE service and the generated Spring Boot service receive the same inputs. Behavioural equivalence is verified at runtime. Migration cycles that previously took six to eighteen months per service now run as a governed, repeatable process."

SCALE (right pillar) — 20 sec

Hundreds of ACE services can run in parallel, each isolated, each through the same governed pipeline — the only serialisation is the approval gates within a single service, which is intentional. And critically — any AI provider. The platform ships with open-source Qwen3 models by default. Any agent's model can be overridden per-project with any approved provider: OpenAI, Anthropic, Azure, or on-premises. Switch providers without changing a pipeline definition. Provider relationships are commercial decisions — not technical constraints."

Q&A — Common questions

Q: What AI models does this use?
"We ship with open-source Qwen3 models — Apache 2.0 licensed — as the system default. There are four model aliases: a reasoning model for analysis, planning and RCA; a smaller reasoning model for orchestration and governance explanations; a coding model for code generation and test engineering; and an embeddings model for the knowledge base and retrieval. Any of these can be overridden per-agent per-project with any approved AI provider, using the Edit Agent configuration. The governance gates are deterministic — they are not made by the AI models. Changing the model cannot bypass a gate."

Q: Who approves at each gate?
"Six named approvers across the pipeline: Service Owner at G0 (proceed decision), Java Architect at G1 (Spring framework template), ACE Subject Matter Expert at G2 (migration specification), Product Owner at G3 (migration plan), QA Lead at G4 (variance disposition), and Release Manager at G5 (production promotion). Each sign-off is SHA-256-bound to the exact artefact reviewed. If anyone submits a revised document after approval, the approval for that document is automatically retired."

Q: Can this platform extend beyond IBM ACE migration?
"Yes — the architecture is not locked to ACE. The agent registry, pipeline engine, model router, and audit ledger are all general-purpose components. The ACE migration factory is the first full production use case. The governance principles — evidence-bound approvals, agent authority contracts, tamper-proof audit — apply to any enterprise process where AI automation needs human oversight. Finance, Legal, and Operations teams could run equivalent governed pipelines using the same structural patterns."

Q: What is the audit trail actually capturing?
"Every agent run, every workflow state transition, every approval, every variance classification, every clarification question and its answer — all recorded in a hash-chained, append-only ledger. Each record captures: the model version used, the prompt version, the agent tool policy version, the approver identity, and the SHA-256 hash of every artefact involved. Modifying any prior record breaks the cryptographic chain and is immediately detectable. For a regulatory audit, this is a query, not a reconstruction exercise."

Q: Can this scale to a full IBM ACE portfolio?
"Yes — by architecture. Every migration job is isolated by job ID. Multiple services can be in-flight simultaneously, each progressing independently through the same governed pipeline. The only serialisation is the human gate approvals within a single service's lifecycle, which is intentional. The database layer is a swap from SQLite to PostgreSQL for scale. Agent workers are stateless and containerisable. The queue is replaceable with SQS or Kafka using the same interface contract."
