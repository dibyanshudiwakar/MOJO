The Migration Request

A migration engineer at Acme Bank opens the ACE Modernization Accelerator portal and submits a new migration job. They fill in a YAML specification — the machine-readable contract that governs everything that follows.

# migration-specification.yaml — submitted at job creation metadata: service: CustomerProfileService sourceCommit: a7f3c91 # exact Git SHA of the ACE source to migrate analysisVersion: "1.0" frameworkTemplateVersion: "3.2" # Spring Boot 3.2 target template source: aceVersion: "12" applications: [CustomerProfileApplication] flows: [GetCustomerFlow, UpdateCustomerFlow, CustomerValidator] esql: [CustomerProfileCompute.esql] schemas: [CustomerProfile.xsd] governance: enabledGates: [G0, G1, G2, G3, G4, G5] iterationLimit: 5 # max remediation cycles before STOPPED

The factory validates this YAML against a JSON Schema contract. If it fails validation, the job stays in CREATED and the errors are returned to the engineer. A SHA-256 hash of the specification is stored as evidence before any agent runs.

Migration Planning — Mapping ACE to Spring

Business: produce a documented plan that architects can review and sign off before any code is written. Technical: generate a deterministic mapping catalogue and an AI-assisted migration plan.

State: FRAMEWORK_BASELINED → ACE_ANALYSED → PLAN_APPROVED
Mapping Catalogue (Deterministic)

The system reads the ACE Inventory and the Framework Template and generates a mapping catalogue: for every ACE construct, it looks up the approved Spring equivalent. Mappings that have no approved target pattern are placed on the Unsupported Mapping Register and must be resolved before the plan can proceed.

ACE Construct Spring Equivalent Status
HTTPInputNode GET /customer/{id} @GetMapping on CustomerController ✓ Mapped
HTTPInputNode PUT /customer/{id} @PutMapping on CustomerController ✓ Mapped
MQInputNode queue CPS.IN @JmsListener with IBM MQ Spring Boot ✓ Mapped
MQOutputNode queue CPS.OUT JmsTemplate.convertAndSend() ✓ Mapped
XSDValidationNode CustomerProfile.xsd Bean Validation + @Valid on DTO ✓ Mapped
ESQL MQMD header propagation Custom MessagePostProcessor ✓ Mapped
ESQL BLOB domain reference — ⚠ Unsupported — clarification raised
AI-Powered
MigrationPlanGenerator
Uses approved LLM via model gateway

What it does: Using the resolved mapping catalogue as grounded input, the planning agent calls the organisation's approved model gateway (governed by the Prompt Registry — only approved prompt versions are accepted). It produces a structured migration plan with rationale, risk register, and a module breakdown for the generated Spring project.

Why AI here? The mapping from ACE architectural patterns to idiomatic Spring Boot requires contextual reasoning: choosing between synchronous and reactive models, deciding how to restructure ESQL transformation logic into service classes, and writing explanatory rationale that architects can evaluate. This cannot be reduced to a lookup table.

Governance constraint: The model gateway rejects any prompt that has not been versioned and approved. It records a PROVIDER_EXECUTION_REQUIRED status — the actual LLM call goes through an approved connector, never directly from application code. Secrets are blocked at the gateway boundary.

SpringProjectGenerator
Uses approved LLM · Produces traceable Maven project

What it does: Translates the approved migration plan into a working Spring Boot project. For each module in the plan, it generates Java classes, configuration files, and unit tests. Differential Testing — Does the New Service Behave the Same?

Business: prove the new service produces identical results to the original for every known scenario. Technical: run both runtimes against the same inputs and compare outputs structurally.

State: BUILD_VALIDATED → DIFFERENTIAL_TESTING → VARIANCE_REVIEW
How Differential Testing Works

The factory constructs a set of canonical test envelopes — pairs of (input, expected output) drawn from the migration specification's test section, production traffic samples (masked), and the ACE Inventory's known interface contracts. Each envelope is run against both the original ACE runtime and the new Spring Boot service. The responses are compared structurally using the DifferentialEvidenceEngine.

Deterministic
DifferentialEvidenceEngine
No AI · Structural deep comparison

What it does: For each test envelope, it applies the comparison policy (masks, ignored paths, numeric tolerances, ordering rules) and performs a deep structural comparison of ACE output vs Spring output. Records a PASS or VARIANCE evidence record for every case. Hashes every evidence record so results cannot be altered after the fact.

Comparison Policy Applied
  • Masks: $.customerId, $.timestamp (sensitive — replaced with [MASKED] in evidence)
  • Ignored paths: $.responseTime, $.traceId (non-functional)
  • Tolerance: ±0.01 on $.creditScore (float rounding)
  • Ordering: significant on $.addressHistory

07

Variance Review — Classifying the Differences

Business: decide which differences matter and which are acceptable. Technical: triage each variance, record a root cause, and choose: accept, remediate, or stop.

State: DIFFERENTIAL_TESTING → VARIANCE_REVIEW → REMEDIATING / READY_FOR_PROMOTION

Three variances were found. The variance review team classifies each one. A variance is not automatically a blocker — some differences reflect intentional improvements (better null handling, safer defaults). The classification determines what happens next.

VAR-001 · TC-10 High MQMD CorrelId format differs

ACE output: "CorrelId": "414d512043505300000..." (hex-encoded bytes)

Spring output: "correlationId": "414d51-2043-5053..." (UUID-formatted string)

Business impact: Any downstream system that reads the CorrelId to correlate MQ messages will break. This is a blocking variance — it must be remediated before promotion.

Decision: REMEDIATE

VAR-002 · TC-11 Medium Null optional field serialisation

ACE output: JSON object omits middleName when absent

Spring output: JSON includes "middleName": null

Business impact: Any client doing strict JSON schema validation against the ACE contract will fail. However, the team confirms that no consumers rely on field absence — they use null checks. The new behaviour is safer.

Decision: ACCEPT (document as intentional improvement in release notes)

VAR-003 · TC-12 High Large payload truncation at 256KB

ACE output: Full 500KB response returned

Spring output: Response truncated at 256KB (Spring Boot default max-http-request-header-size misconfigured)

Business impact: The bulk-export endpoint will silently truncate data for large customers. Blocking.

Decision: REMEDIATE

Variance Review outcome: 2 variances require remediation (VAR-001, VAR-003). 1 variance accepted (VAR-002). The job transitions to REMEDIATING. If both remediations succeed, differential testing reruns automatically.

Remediation — Fixing the Variances

Business: close the gaps found in testing. Technical: run the confidence engine, apply approved patterns, and re-test.

State: VARIANCE_REVIEW → REMEDIATING → IMPLEMENTING → DIFFERENTIAL_TESTING
AI-Powered
ConfidenceRemediationService
Uses approved LLM · Evidence-weighted scoring

What it does: For each variance requiring remediation, the service computes a confidence score by weighting the available evidence: how well-understood is the root cause? Does an approved fix pattern exist in the knowledge index? Are there tests that cover the fix? Based on this score, it routes the variance to either a direct fix (applies the approved pattern automatically) or a clarification (a human must decide).

VAR-001 — MQMD CorrelId format
1
Root Cause Analysis
Spring's JmsTemplate generates a UUID-format correlation ID by default. The ACE MQMD node writes the raw byte array as hex. Root cause: MqAuditGateway.java does not implement a custom MessagePostProcessor to preserve the ACE hex format.
2
Confidence Score
Evidence: root cause is clear (0.9), approved pattern exists in knowledge index (MqHexCorrelIdPostProcessor — pattern KB-042), test TC-10 covers the fix (0.85).
0.88 — Direct Fix Eligible
3

The approved pattern MqHexCorrelIdPostProcessor is injected into MqAuditGateway.java. A rollback pointer is recorded (previous JAR hash). TC-10 is re-run and passes.
VAR-003 — Large payload truncation
1
Root Cause Analysis
Spring Boot's server.tomcat.max-swallow-size and spring.mvc.async.request-timeout defaults are too low for this service's bulk-export workload. Root cause: framework template v3.2 does not set a payload size override for bulk endpoints.

Root cause clear (0.85), approved pattern exists (BulkEndpointSizeConfig — pattern KB-019), but the max safe payload size for this service's SLA is unknown. Score drops.

What the client can tell their stakeholders

The Customer Profile Service has been migrated from IBM ACE v12 to Spring Boot 3.2. The migration factory ran 7 agents across the pipeline — 4 deterministic (fully auditable, no AI) and 3 AI-powered (each with a human approval gate before its output could advance). Every decision — from the initial specification through to the final promotion — is recorded with evidence hashes, approver identities, and timestamps. If any question arises about why a particular line of code was generated, the provenance manifest traces it back to the original ACE flow in under a minute.

The service passed 12 behavioural equivalence tests. Two differences from the original were found and fixed using approved engineering patterns from the organisation's knowledge index. One difference was accepted as an intentional improvement. The full evidence package is available for compliance, audit, and future reference.
