What Is the Skill

The IIB-to-MS Migration Skill is a Claude Code skill (loaded via external-skills/iib-to-ms-migration/SKILL.md) that guides an LLM session through migrating IBM Integration Bus (IIB/ACE) message flows into CVS Health-standard Spring Boot 3.2.2 / Java 21 microservices deployable on OpenShift. It is not a standalone code generator — it is a governed, step-by-step instruction set binding CVS Health's internal EIP framework conventions, mandatory rules, and known defect patterns into a repeatable migration workflow.

Entry Point
external-skills/iib-to-ms-migration/SKILL.md
Defines the 4-stage workflow, connector type routing, 13 mandatory rules, HANDOFF-C smoke test (added 2026-10-09), and state.json contract.
Workflow Stages
INTAKE → SCAFFOLD → GENERATE → HANDOFF
Each stage has explicit inputs, outputs, and blocking conditions enforced via state.json.
Connector Types (5)
QL/CICS + Camel Bindy · RxClaim SBO XML/JAXB · REST External/Direct · IBM MQ + COBOL Copybook · SOAP
Reference Library (7 files)
Mandatory rules, 16 defect patterns, 25+ gap items, workflow state contract, structural conventions, fixed-file templates, config-map baseline.

Key Hard Constraints

  • Framework version: 3.2.2, Java: 21 (defaults; override via state.json framework_version)
  • Base Docker image: quay-registry.aetna.com/cvs-base-images/os-eng/redhat/ubi9/openjdk-micro:21
  • No QLRequest.builder(), no RestTemplate, no Kong token-validator, no custom exception classes
  • Always Camel Bindy for QL/CICS; CVS encrypt-credential endpoint by default
  • Timeout must return HTTP 408, not 500; COBOL signed-decimal: N+1 bytes
  • EieHeader uses real accessors only (no direct field access)
  • application.properties: 1–7 lines; application-local.properties: 16–97 lines
  • SPRING_CONFIG_LOCATION replaces (does not supplement) defaults

Usability Assessment

Modular Agent Design — Independently Testable
Each agent inherits from BaseAgent (app/agents/base.py) with declared AGENT_ID, TOOLS, OUTPUTS, and optional PROMPT. Any agent runs standalone via python -m app.agents.<module> --help. The IMPLEMENTATIONS dict in app/agents/__init__.py maps all 14 agent IDs to their classes; adding IIB-specific logic to a service does not require touching any other agent.
Artefact-Bound Approvals
Every gate approval in FactoryService._valid_approvals() binds to artefact content_hash values via artifact_bindings. An approval cannot be reused against a different version of an artefact. The EvidenceRef dataclass in app/agents/base.py computes content_hash = digest(content) — the hash is what the gate approves, making every approval traceable to a specific artefact state.
Connector Type Overrides Already Supported
MappingAndPlanningService.create_mapping_catalogue() in app/services/migration_lifecycle_v6.py accepts an overrides dict that merges with DEFAULT_MAPPINGS. The skill's 5 IIB connector types can be registered as additional mapping keys without modifying any file — just pass them via context.param('overrides') from MigrationOrchestratorAgent._params('planning', ...).
Clarification Blocking Already Wired
Open clarifications block lifecycle advancement via validate_transition() in app/domain/state_machine.py. FrameworkBaselineAgent already creates Clarification(stage='FRAMEWORK_BASELINE', owner='JAVA_ARCHITECT') per conflict. Adding IIB mandatory rule violations as clarifications requires only calling repo.insert() into the clarifications table — the blocking mechanism is already in place.
LLM Reasoning via ReasoningGateway
Agents needing model reasoning call ReasoningGateway(repo).reason(context, prompt_name, payload). The deterministic classification is always authoritative; model output is a second opinion in metrics. Prompt names are stable governed strings. A disagreement between model and deterministic result is recorded in run metrics for auditability.
WAITING_G0–G5 Gate-Hold States
The state machine in app/domain/state_machine.py has explicit WAITING_Gx states for every gate. A job that requires a human to sign a gate transitions to WAITING_G2 etc., then resumes to the post-gate target when the approval is granted. The orchestrator's GATE_FIRST set uses these states to avoid running agents before the gate is satisfied.

LLM Provider Integration — Anthropic API Key, End to End

Every agent in the Factory currently runs in deterministic mode. No real Claude call ever happens, even though the skill files contain the prompts and the ReasoningGateway is wired in. This part explains exactly why, what must be built to activate it, and how to wire the CVS Anthropic key so the Factory produces model-assisted results for every agent that benefits from reasoning.

⚠ Current state: AgentContext.provider = None for every agent (see app/agents/base.py:108). Until you complete all three steps in this part, no agent ever calls Claude — not even partially.

Why the Factory Runs Deterministically Today

There are three independent blockers, all of which must be cleared before a real API call can complete. ReasoningGateway.reason() checks them in order and short-circuits at the first failure.

#BlockerLocation in CodeHow It Manifests
1 No APPROVED prompt or model in DB app/agents/reasoning.py:90–93 provenance.reason = 'no_approved_prompt_or_model'; returns (None, provenance) immediately
2 DLP policy refuses the payload app/agents/reasoning.py:94–103 AIRegistryService.gateway_request() raises ValueError; provenance records 'gateway_refused:…'
3 context.provider is None app/agents/reasoning.py:108–110 provenance.reason = 'no_provider_execution_adapter'; returns (None, provenance) — even if blockers 1 and 2 are cleared

Clearing blocker 3 alone does nothing if blockers 1 or 2 remain. The three steps below address all three in the correct order.

Step 1 — Create the AnthropicProvider Class

The seam is ProviderExecutionAdapter defined in app/agents/reasoning.py:45–55. Implement it as a new file app/providers/anthropic_provider.py:

# app/providers/anthropic_provider.py
import json, os
import anthropic
from app.agents.reasoning import ProviderExecutionAdapter

class AnthropicProvider(ProviderExecutionAdapter):
    """Wraps the Anthropic Python SDK.

    template  — the 'template' column from prompt_registry (plain text).
    payload   — the dict the agent assembled; serialised as user message.
    Returns a JSON-serialisable dict that ReasoningGateway stores as the
    completion and passes back to the agent as its 'answer'.
    """
    def __init__(self, model: str = "claude-opus-5-5", max_tokens: int = 4096):
        api_key = os.environ.get("CVS_ANTHROPIC_KEY") or os.environ.get("ANTHROPIC_API_KEY")
        if not api_key:
            raise RuntimeError("CVS_ANTHROPIC_KEY env var not set")
        self.client = anthropic.Anthropic(api_key=api_key)
        self.model = model
        self.max_tokens = max_tokens

    def invoke(self, template: str, payload: dict) -> dict:
        message = self.client.messages.create(
            model=self.model,
            max_tokens=self.max_tokens,
            system=template,
            messages=[{"role": "user", "content": json.dumps(payload, default=str)}],
        )
        text = message.content[0].text
        try:
            return json.loads(text)
        except json.JSONDecodeError:
            return {"raw": text}

pip install anthropic
ℹ Why system + user? The template column in prompt_registry contains the governed prompt text (e.g. "You are given deployment and telemetry evidence…"). Passing it as the system message keeps it separate from the payload data, which is the pattern all 8 prompt templates in config/agent-prompts.v1.json are designed for.

How Skill Files Become Prompt Text

This is the connection between the external-skills/iib-to-ms-migration/SKILL.md file and the Anthropic API call:

1. Skill file = authoring source
SKILL.md is the human-readable specification that was used to author the 8 prompt templates in config/agent-prompts.v1.json. It is not loaded at runtime by the Factory's code.
2. Prompt templates = governed text
Each template is the distilled, governed version of the skill's intent for one agent step. It is stored in prompt_registry.template after registration and approval.
3. Payload = agent-assembled data
Each agent builds a payload dict from its job context (evidence, ACE model, test results, etc.) and passes it to ReasoningGateway.reason(context, prompt_name, payload).
4. API call = template + payload → Claude
AnthropicProvider.invoke(template, payload) sends the template as the system message and the serialised payload as the user message. Claude's JSON response becomes the agent's answer.
